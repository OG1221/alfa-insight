# Развёртывание и сдача

## Проверенный Docker

25 октября 2026 реально выполнены Docker Compose build/up на Linux ARM64 через Colima. PostgreSQL 16.8 и приложение healthy. Проверены HTTP, 6 браузерных сценариев и OCR Tesseract rus+eng. Локальный контрольный адрес: http://127.0.0.1:18081. Основной стенд с официальными данными: http://127.0.0.1:8000.

Обычный запуск на машине с Docker:

```sh
cp .env.example .env
docker compose up --build -d
```

Открыть http://127.0.0.1:8000. Для другого порта — APP_PORT=18081 в .env. PostgreSQL не публикуется наружу. Не удалять рабочий volume командой down -v.

На этой машине переносимые инструменты находятся в runtime/tools/bin, не меняют глобальный Docker context. Для повторного управления контрольным стендом:

```sh
export PATH="$PWD/runtime/tools/bin:$PATH"
export DOCKER_CONFIG="$PWD/runtime/docker-config"
export DOCKER_HOST=unix:///Users/mariapiskun/.colima/default/docker.sock
docker compose -p alfa-insight-check ps
```

При повторном up использовать прежние секреты окружения/пароль базы: новый пароль в Compose не изменит пароль уже инициализированной БД. Эти значения не предназначены для постоянного внешнего размещения.

## Внешняя ссылка

Постоянный публичный хостинг не настроен. Предложен Render, но аккаунт хостинга не подключён. Sites выполняет Workers и не размещает данный Python/PostgreSQL стек. Платный тариф не подключался.

Подготовлено отдельное синтетическое демо на порту 18080: scripts/public_demo.py создаёт изолированную схему и случайный токен администратора, запрещает запуск с официальными данными. Docker-контрольный стенд также содержит только синтетические профили. Попытки временного Cloudflare Quick Tunnel столкнулись с ошибкой SRV DNS; после отдельного DNS в контейнере разрешение имён заработало, но соединения QUIC и HTTP/2 до Cloudflare edge недоступны; выданные имена без проверки HTTP не считаются рабочими ссылками и не передаются как URL для сдачи.

## Постоянный сервер

1. Использовать доступный Linux-сервер с Docker и постоянным диском. Тариф с оплатой требует отдельного решения пользователя.
2. Передавать только код и синтетические данные. Не копировать runtime, .env, data/private и банковские оригиналы без подтверждённых прав.
3. Сгенерировать ADMIN_TOKEN, DEMO_TOKEN, POSTGRES_PASSWORD. Хранить в секретах хостинга. Для чувствительных данных отключить анонимный доступ и добавить полноценный вход с ACL.
4. Перед loopback-портом приложения поставить HTTPS reverse proxy, настроить timeout и лимит размера. Добавить outbound proxy с закреплением IP для защиты от DNS rebinding.
5. Проверить /api/health, создание и разбор новой новости, отказ неавторизованного доступа, источники и мобильный путь. Только после HTTP и браузера записать настоящий URL.
6. Резервировать pgdata через pg_dump и проверить восстановление. Не писать токены и ключи в логи.
